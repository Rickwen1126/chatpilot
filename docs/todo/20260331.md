## Multi-Line Route Key Migration

### 決策

- multi-line 上線後，系統全面以新的 named route key 為準
  - 例如 `line:shinyipaint:C...`
- 舊的 legacy key 不作為持續相容層
  - 例如 `line:C...`
- 舊 key 對應的舊資料先保留
  - 視為歷史資料 / 測試資料 / fallback 參考
- 對重要資料採用 **copy-based migration**
  - 複製到新 key
  - 不直接刪除舊 key

### 問題定義

- 這不是單純的 adapter bootstrap 過渡問題
- 真正的風險是 canonical route key 從 `line:C...` 變成 `line:{channel}:C...` 後，
  系統會把同一個真實 LINE 對話拆成兩個不同 target
- 影響範圍包含所有以 `route_id` 為 key 的資料：
  - session context metadata
  - route labels
  - memory store 內的 route-scoped records
  - reminder / schedule
  - task history
  - custom prompts / observer / permission 相關資料

### 待辦

- 盤點 shinyipaint 相關、目前仍掛在 legacy `line:*` key 底下的重要資料
- 列出需要 migration 的資料類型與來源檔 / store
- 定義 legacy key → named key 的對應規則
  - `line:C...` → `line:shinyipaint:C...`
  - `line:U...` → `line:shinyipaint:U...`
- 先做 copy，不做 move
  - 新 key 建立後保留舊資料
  - 避免一次性切換造成資料遺失或回滾困難
- 優先處理 shinyipaint 真正會影響線上行為的資料
  - labels
  - reminder / schedule
  - custom prompts
  - observer / memory 類資料
  - task history（若有營運價值）
- 補 migration 驗證
  - 同一個真實對話在 named key 下可讀到複製後的重要資料
  - 舊 key 保留但不再作為主要寫入目標

## Session Identity 設計債

### 問題定義

- 目前 `sdk_session_id` 仍然由 `route_id + chatbot_name` 組成
- 這在短期內是可接受的 shortcut，但長期會遇到同一類問題：
  - route migration 時 session continuity 被切斷
  - chatbot rename / route rename 直接改變 runtime identity
  - delegated async / 多節點時，derived identifier 被誤當成真正 identity

### 目前判斷

- `SessionContextRegistry` 以 `sdk_session_id` 為 key 這件事本身沒有問題
- 真正有風險的是：
  - `sdk_session_id` 的生成策略目前仍是 derived composition
- 這和 file 設計上「source fields 不該直接當 primary key」是同一類壓力

### 暫時結論

- 現在先不重做 session identity
- 目前 `sdk_session_id = route_id + chatbot_name` 仍可接受，因為：
  - local-first 單機模型還撐得住
  - `SessionContextRegistry` 已經把 parse 依賴降下來
- 但這應被視為 **明確的設計債**，不是長期最終方案

### 未來方向

- 升級為：
  - opaque `sdk_session_id`
  - `(route_id, chatbot_name) -> sdk_session_id` 的正式 binding / mapping
- 讓 route identity 與 runtime session identity 脫鉤
- 這樣 route migration、chatbot rename、session continuity 才能分開處理

### 觸發重構的條件

- 需要保留 route migration 前後的 session continuity
- 需要跨機器 / 多節點共享 session control plane
- 需要讓 chatbot rename / route rename 不影響 SDK resume identity
- 需要更明確區分：
  - runtime actor identity
  - target route identity

### 待辦

- 把目前 `sdk_session_id` 的使用面盤點清楚
  - SDK resume
  - workspace path
  - response injector
  - session context metadata
- 評估如果改成 opaque session id，需要新增哪些 binding store / migration
- 未來若開始做 file handle / file asset DB，可一起對齊：
  - internal opaque primary key
  - domain/source fields 作為 unique lookup，而不是 primary key

## Observer / Memory Unit 下一輪重構主題

參考：
- [`docs/reference/observer-memory-group-model.md`](../reference/observer-memory-group-model.md)

### 目前已確認的現況

- 目前持久記憶層的主單位是 `route_id`，不是 `chatbot_name` / bot type
  - `MemoryStore` protocol 直接定義為 route-scoped store
  - 記錄 key 的心智模型是 `(route_id, type, id)`
- 主要持久表：
  - `memory_memos`
  - `memory_custom_prompts`
  - `memory_reminders`
  - `memory_schedules`
  - `memory_observations`
  - `trigger_keywords`
  都是以 `route_id` 作為主要 ownership key
- 目前只有少數欄位帶 `chatbot_name`
  - 例如 `memory_schedules.chatbot_name`
  - 但這只是 delegation/origin metadata，不是 bot-scoped memory bucket
- 也就是說，今天系統沒有一個正式的「以 bot 為單位的持久記憶層」
  - 現況更像：
    - route memory 為主
    - bot/session/toolset 是 runtime 行為層
    - observer source map 是 query/capture policy，不是另一套 memory store

### 為什麼現在的 observer 註冊方式會有風險

- 目前 observer 看起來像一種 bot mode，但實際上它混了三件不同的事：
  - 要不要回話
  - 要不要持續 background capture / summarize
  - 這份背景記憶要不要給別的 chatbot / route 查
- 因為記憶主單位其實是 route，不是 bot
  - 所以今天 observer 的 registration / source map 其實只是「在 route memory 上再疊一層 capture/query policy」
  - 不是一個真正穩定的 bot-memory 抽象
- 這會讓後面變得難處理：
  - 平常不回話、但需要一直理解整段討論串的 chatbot
  - 不同 chatbot 之間是否共享背景記憶
  - 同一個 chatbot 在不同 route 上使用不同 capture / reply 策略

### 目前可先收斂的三個能力維度

- `memory sharing`
  - 這份背景記憶給誰用、共享範圍是什麼
- `background context capture`
  - 是否持續 ingest / batch observe / summarize
- `reply policy`
  - `silent` / `trigger_only` / `auto_reply`

### 重要提醒

- 上面三軸是下一輪的 design direction
- 不是現在已經存在的 DB schema
- 所以不能誤以為目前系統已經有：
  - bot-level memory
  - shared memory layer
  - 可自由組裝的 observer policies

### 下一輪重構的核心目標

- 明確定義：
  - 現在有哪些 memory unit
  - 哪些是 route-scoped
  - 哪些只是 runtime/session metadata
  - 如果要做 bot-level / shared memory，需要新增哪一層 ownership/linking model
- 在這個抽象清楚前，不再把 observer 擴成更多 ad-hoc special case
- 這會是下一個「要 refactor 到真正可用的大功能」，不是 patch 級修正

#### 問題定義

  - 工具權限過大導致的本機破壞
