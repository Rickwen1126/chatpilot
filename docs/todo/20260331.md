## Multi-Line Route Key Migration

### 決策

- multi-line 上線後，系統全面以新的 named route key 為準
  - 例如 `line:shinyipaint:C...`
- 舊的 legacy key 不作為持續相容層
  - 例如 `line:C...`
- 舊 key 對應的舊資料先保留
  - 視為歷史資料 / 測試資料 / fallback 參考
- 對重要資料採用 **copy-based migration**
  - 複製到新 key
  - 不直接刪除舊 key

### 問題定義

- 這不是單純的 adapter bootstrap 過渡問題
- 真正的風險是 canonical route key 從 `line:C...` 變成 `line:{channel}:C...` 後，
  系統會把同一個真實 LINE 對話拆成兩個不同 target
- 影響範圍包含所有以 `route_id` 為 key 的資料：
  - session context metadata
  - route labels
  - memory store 內的 route-scoped records
  - reminder / schedule
  - task history
  - custom prompts / observer / permission 相關資料

### 待辦

- 盤點 shinyipaint 相關、目前仍掛在 legacy `line:*` key 底下的重要資料
- 列出需要 migration 的資料類型與來源檔 / store
- 定義 legacy key → named key 的對應規則
  - `line:C...` → `line:shinyipaint:C...`
  - `line:U...` → `line:shinyipaint:U...`
- 先做 copy，不做 move
  - 新 key 建立後保留舊資料
  - 避免一次性切換造成資料遺失或回滾困難
- 優先處理 shinyipaint 真正會影響線上行為的資料
  - labels
  - reminder / schedule
  - custom prompts
  - observer / memory 類資料
  - task history（若有營運價值）
- 補 migration 驗證
  - 同一個真實對話在 named key 下可讀到複製後的重要資料
  - 舊 key 保留但不再作為主要寫入目標

## Session Identity 設計債

### 問題定義

- 目前 `sdk_session_id` 仍然由 `route_id + chatbot_name` 組成
- 這在短期內是可接受的 shortcut，但長期會遇到同一類問題：
  - route migration 時 session continuity 被切斷
  - chatbot rename / route rename 直接改變 runtime identity
  - delegated async / 多節點時，derived identifier 被誤當成真正 identity

### 目前判斷

- `SessionContextRegistry` 以 `sdk_session_id` 為 key 這件事本身沒有問題
- 真正有風險的是：
  - `sdk_session_id` 的生成策略目前仍是 derived composition
- 這和 file 設計上「source fields 不該直接當 primary key」是同一類壓力

### 暫時結論

- 現在先不重做 session identity
- 目前 `sdk_session_id = route_id + chatbot_name` 仍可接受，因為：
  - local-first 單機模型還撐得住
  - `SessionContextRegistry` 已經把 parse 依賴降下來
- 但這應被視為 **明確的設計債**，不是長期最終方案

### 未來方向

- 升級為：
  - opaque `sdk_session_id`
  - `(route_id, chatbot_name) -> sdk_session_id` 的正式 binding / mapping
- 讓 route identity 與 runtime session identity 脫鉤
- 這樣 route migration、chatbot rename、session continuity 才能分開處理

### 觸發重構的條件

- 需要保留 route migration 前後的 session continuity
- 需要跨機器 / 多節點共享 session control plane
- 需要讓 chatbot rename / route rename 不影響 SDK resume identity
- 需要更明確區分：
  - runtime actor identity
  - target route identity

### 待辦

- 把目前 `sdk_session_id` 的使用面盤點清楚
  - SDK resume
  - workspace path
  - response injector
  - session context metadata
- 評估如果改成 opaque session id，需要新增哪些 binding store / migration
- 未來若開始做 file handle / file asset DB，可一起對齊：
  - internal opaque primary key
  - domain/source fields 作為 unique lookup，而不是 primary key

### 已確認 bug：目前圖片無法真正餵給 Copilot/Claude vision

#### 問題定義

- 目前 repo 內的圖片/媒體「餵給模型」路徑，依賴的是：
  - 純文字 prompt 中的 `[圖片 ref:...]`
  - tool `download_media`
  - `ToolResult.binaryResultsForLlm`
- 但目前本機 Python Copilot SDK 實作並沒有把 `binary_results_for_llm` 往 RPC result 傳上去
- 因此這條路下，模型實際上看不到圖片 bytes

這不是「只有 Claude 不吃圖」而已，
而是 **以目前 Python SDK 版本來看，tool binary image payload 根本沒有被送進模型**。

#### 證據

- repo 目前路徑：
  - `src/chatpilot/pipeline/samples/batch_vision.py`
    - 只送純文字 prompt，要模型自己呼叫 `download_media`
  - `src/chatpilot/tools/builtin/download_media.py`
    - 下載後回傳 `binaryResultsForLlm=[{data, mimeType, type: "image"}]`
- repo 的 SDK wrapper：
  - `src/chatpilot/sdk/session.py`
    - `send_and_wait()` 目前只送 `{"prompt": message}`
    - 沒有使用 `attachments`
- 本機 Copilot SDK：
  - `copilot/types.py`
    - `MessageOptions` 支援 `attachments`
    - attachment 類型是 `file | directory | selection`
  - `copilot/session.py`
    - `send()` / `send_and_wait()` 都接受 `attachments`
  - `copilot/session.py` + `copilot/client.py`
    - tool result transport 只序列化 `text_result_for_llm` / `result_type` / `tool_telemetry`
    - 沒有把 `binary_results_for_llm` 傳到 RPC result

#### 補充 mismatch

- repo 裡目前多個 tool 仍使用 camelCase 風格建 `ToolResult`
  - `textResultForLlm`
  - `resultType`
  - `binaryResultsForLlm`
- 但本機 Python Copilot SDK dataclass 使用 snake_case：
  - `text_result_for_llm`
  - `result_type`
  - `binary_results_for_llm`

這表示 repo 目前對 `ToolResult` 形狀的假設，和本機安裝 SDK 並不一致。

#### 暫時結論

- 若要讓 Claude / Copilot vision 真正吃到圖片，方向應改成：
  - 先將圖片下載 / materialize 成 local file
  - 再用 `session.send(...)` / `send_and_wait(...)` 的 `attachments=[{"type":"file","path":"..."}]`
- 也就是：
  - file bytes / local asset 應由 `FileHandleCenter` 或相關 preprocessor 準備
  - vision pipeline / chatbot 再透過 message attachment 把圖片送進 SDK

#### 待辦

- 驗證本機可用 Claude models 的 `supports.vision` / `limits.vision`
- 做最小 POC：
  - local image file
  - `attachments=[{"type":"file","path":"..."}]`
  - 確認 Claude vision model 能否實際讀圖
- 若 POC 成立，重寫 batch vision / image analyze path
  - 改用 local file attachment，而不是 `download_media` tool binary result

## System Security Boundary / Agent Containment

### 問題定義

- 這不是單純的 file virus scan 問題
- 更大的議題是：
  - 如何防止 agent / tool 破壞系統本身
  - 如何防止外部輸入透過檔案、工具或 async mission 破壞本機環境
- 也就是 system security boundary，需要和 FileHandleCenter 分開討論

### 目前觀察

- `show_image` / file exposure 已經顯示：
  - 安全判斷不只取決於 scan status
  - 還取決於 file origin、relation lineage、route scope
- 更廣泛來看，未來 agent 若能 create file、modify file、執行 async mission，
  風險不只在檔案內容，也在：
  - 工作目錄污染
  - 任務執行時對本機環境的副作用
  - 工具權限過大導致的本機破壞

### 待討論方向

- system file boundary 與 workpath boundary 要不要進一步收緊
- agent 可操作的 local file scope 要如何限制
- tool / async mission 是否要有更明確的 capability boundary
- 高風險 async mission 是否應考慮放進更強隔離環境
  - 例如 container / Docker
- 如何區分：
  - 一般 file governance
  - 系統安全 containment

### 暫時結論

- 這題先獨立記錄，不併入本輪 FileHandleCenter 設計
- 目前先以 FileHandleCenter 解決：
  - file ingress 治理
  - file lineage
  - file exposure policy
- 更大的 agent containment / system hardening，後續另開一輪設計討論
