## Observer 抽象進一步收斂

### 目前的核心判斷

- observer 現在能用，但抽象不穩
- 真正的持久記憶單位仍然是 `route_id`
- observer 現在混了三件事：
  - reply policy
  - background capture
  - shared query / memory sharing

### 高一層收斂

- 先不要往 event schema 鑽
- 下一輪 observer 應先被定義成：
  - 一種 route-level / binding-level observation capability interface
  - 而不是 bot type

### 關鍵修正

- `observation` 不應掛在 `chatbot`
- 應掛在 `binding`
- 原因：
  - chatbot 是能力單位 / persona / tools / model
  - observation 雖然像能力，但本質是「這條對話如何使用這個能力」
  - 同一個 bot 在不同 route 上，可能需要不同的 capture / consume / reply 行為

### 目前可接受的高層模型（已被 2026-04-03 定案覆蓋）

- `route_id`
  - storage unit
- `group`
  - query / sharing unit
- `binding.reply_policy`
  - 這裡當時先記成 `silent` / `trigger_only` / `normal`
  - 後續已收斂成：
    - `silent`
    - `addressed`
    - `smart`（future）
- `binding.observation`
  - capture / consume policy

### 重要設計方向

- `route-local storage + group-level sharing`
- transport / memory / interaction 三層解耦
- 這也自然打開 cross-platform shared memory 的可能性
  - 但這應是 `group` abstraction 的自然結果，不是第一優先的直接目標

## Discovery Hook / 預設 Profile Onboarding

### 背景

- 目前如果 route discovery 只能靠第一則 message
  - 想把新 route 設成 silent / observer 會有風險
  - 因為「第一下 discovery message」可能先走到 default bot 並回話
- 把 default bot 全設 silent 不是合理解法

### 已收斂的方向

- `follow` / `join` 應支援 pre-message route discovery
  - `follow`：先知道私聊 `user_id`
  - `join`：先知道 bot 被加入的 `group_id`
- 再結合：
  - `get_profile`
  - `get_group_summary`
  做名稱反查與 label enrichment

### 預設 profile onboarding

- discovery 當下就套用預設 route profile
- profile 可包含：
  - `chatbot`
  - `reply_policy`
  - `observation`
  - 其他 route-level policy

### matching 優先序（暫定）

- exact `group_id` / `user_id`
- 名稱 keyword match
- channel-scoped default
- global default

### 和 observer 的關係

- 這題和 observer 有關，但不是同一個 milestone
- observer 核心先解：
  - memory unit
  - sharing unit
  - binding policy
- discovery onboarding 後做：
  - route 預先初始化
  - 安全地套 silent / capture / consumer profile
