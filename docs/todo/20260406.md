## Active Backlog

### P1 — 下一段直接討論 / 最有產品價值

1. STT prompt shaping
   - 現況：
     - transcript 太像「音檔內容解釋」
     - 對話感不夠自然
   - 收斂後方向：
     - 正式做法不是讓模型 `auto` 猜，而是提供 route-scoped system slash command：
       - `/audio conversational`
       - `/audio transcript`
       - `/audio analysis`
     - 這是這題的正解答，因為它直接把 audio handling intent 綁到 `route_id`
   - 目標：
     - `conversational`
       - transcript 更像使用者原句
       - audio provenance 留在 hidden/system context
       - chatbot 把語音當一般對話接住，而不是先解釋逐字稿
     - `transcript`
       - 直接把逐字稿回給使用者，不走一般聊天接話語氣
     - `analysis`
       - 把音訊當分析素材，而不是普通對話輸入
   - 後續要補：
     - route-scoped audio mode state / slash command 設計
     - 各 mode 下的 prompt / message shaping
     - regression E2E

2. route-level recent file recall
   - 現況：
     - `show the last image again` 仍偏 session-history
     - 目前高層處理主線明確的主要還是 `image` / `audio`
     - `file` / `video` 雖已納管進 canonical file flow，但大多仍是 ref-first / on-demand tool 使用
   - 目標：
     - 改成 route-level recent file lookup
     - 不依賴當前 session 還記得那張圖
   - 後續要補：
     - route recent-file query model
     - regression E2E

3. observation retrieval capability design
   - 現況：
     - `query_observations` 的 path 已經漂亮且穩定：
       - `route_id` permission
       - `group -> source routes`
       - route-scoped DB query
     - 現在真正偏弱的是 tool surface 與 retrieval capability，本質上還是 group-based / exact-filtered lookup
   - 已確認的中間解法：
     - binding rule 應動態進入 system prompt
     - `route_group` 應提供 description
     - `query_observations` tool 應把 `group name -> description` 一對一列表暴露給 LLM
     - 這樣 LLM 不需要硬背 `shinyipaint_ops`，而是能靠 route 當前可 consume 的 groups + desc 做語意對應
   - 真正大的下一題：
     - retrieval tool 要怎麼保持簡單，但又足夠 powerful
     - path 本身不是 blocker，重點是 tool/query surface 與 DB/query model 的演進
   - 後續要補：
     - route-scoped observation access hint 設計
     - group description 注入策略
     - retrieval tool capability 設計（time / person / category / summary / free-form query）
     - regression E2E
